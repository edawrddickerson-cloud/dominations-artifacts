# Crafted item log statistics

## Crafting Probability

The calculator appears above the dashboard on Crafting Stats. Personal / Community follows the page view; Hall and artifact category are explicit calculator inputs. Hall changes on the page also update the calculator. The perk picker uses that Hall/category's observed pool and current sample only; it never offers the whole cross-category canonical registry. Known pool perks remain selectable without sample counts; missing observations produce a No sample result naming the affected perks instead of disabling their checkboxes. Changing Hall/category drops selections outside its pool. Table search, position and Collection Target filters do not change whole-card odds. Calculator drafts persist locally under `dn-crafting-probability-v1`; they never modify profiles, capture history, inventory or consent.

Each of up to five requirements selects one or more canonical perks, a count, At least / Exactly, Combined / Same perk, and Tier: Any / Max. Main tiers are 1/6/11 and War tiers are 1/3/6; magnitudes include canonical negative signs. Combined counts any mixture of selected perks. Same perk requires the count within one selected perk. Exactly on a combined selection limits the total matching rows; Exactly on a same-perk group requires at least one selected perk with exactly that many matching rows. Requirements are ANDed, anywhere on the five-row card, with each physical row assigned to at most one requirement. Unassigned rows remain unrestricted except for exact-count constraints. Overlapping selections cannot reuse a row. Counts totaling more than five are rejected.

The user-confirmed game constraint is at most two copies of a canonical perk at the same tier. Max selects the best legal tier mix for the requested count: for one perk, counts 1–5 require high; 2 high; 2 high + 1 mid; 2 high + 2 mid; and 2 high + 2 mid + 1 low respectively. A Same perk group uses that pattern within one candidate perk. A Combined group can use more top-tier rows across distinct perks (for example, three high rows across two perks), retaining the two-per-perk/tier cap. Each requirement displays its resulting mix. Saved numeric-tier requirements migrate to Max; matching legacy requirements for the same perk/group are combined by count.

`crafting-probability.js` evaluates the five-row distribution exactly **under the model**. Perk choices use independent draws with pooled empirical row frequencies for the selected Hall/category. For each perk's count, category-level tier frequencies supply weights, normalized over legal allocations with at most two copies per tier. Thus Any odds retain the empirical perk-count model and do not change by event, while Max uses the capped tier distribution. This is an explicit conditional-allocation assumption, not a verified account of the game's generation or reroll algorithm; the constraint alone does not establish exact odds. The cap is applied to the full count of every selected perk, not separately to each requirement. A generating-function dynamic program retains every feasible disjoint requirement assignment per outcome, so multiple valid allocations and same-perk candidates do not inflate odds. Trials use `1 - (1 - p)^n`, evaluated stably; 1 in N is a reciprocal rate, not a guarantee.

Calibration `inferred-october-2026-v1` uses UTC observations from 13 October inclusive to 19 October exclusive for During event, and 20 October inclusive to 25 October exclusive for Outside event. These are inferred historical sample periods, **not** a verified event boundary or labels assigned to encounters. No later date is automatically classified as outside an event. The advertised fivefold top-tier boost is not used to invent the other tier probabilities. The actual available calibration counts are used, separately by Hall/category. Any-tier questions do not use tier profiles, so their estimates do not change with the event selector.

Personal model inputs derive from the existing community eligibility projection over the canonical history. Community inputs prefer `planner_crafting_probability_model(text,text)`, added by `202610250006_crafting_probability_model.sql`. This read-only aggregate RPC exposes counts only; it excludes withdrawn consent, tombstones, expired/future evidence, exclusions and invalid starting ranges. It neither assigns event IDs nor exposes owners, encounters or private history. Existing reports and their event filters are unchanged. When the new RPC is absent, the calculator uses the existing filtered `planner_crafting_summary` perk counts and historical aggregate tier profiles, so local Community mode does not require a database change. Transport failures do not masquerade as a missing migration.

`data/crafting_probability_calibration.js` contains versioned historical aggregate tier counts, with no encounter or account data. If a selected period has fewer than 20 artifacts or lacks an observed requested tier, an available historical profile for the same Hall/category supplies the tiers. The status explicitly reads Historical community tiers and gives the tier-sample artifact count. These reference aggregates are a fixed model calibration, not a live contribution count. Rebuild with `node scripts/build_crafting_probability_calibration.cjs --input=PRIVATE_BACKFILL_PLAN.json` after reviewing a replacement sample.

Missing perks, requested tiers unobserved even in the reference sample, and absent tier profiles return insufficient data instead of fabricated zero odds. A nonempty small profile can still produce a low-sample estimate when no larger reference exists. Low sample is flagged for selected perks below 20 observed rows or tier profiles below 100 artifacts. Zero resulting from incompatible requirements is a model outcome, not proof that a game perk is unavailable. The UI reports sample counts and model assumptions; it does not display a confidence interval from a single marginal Wilson interval. OCR error, missed/repeated encounters, eligibility selection and untested dependencies can affect estimates, especially rare combinations. War never silently borrows Main data.

`node scripts/check_crafting_probability_calibration.cjs --input=PRIVATE_LOG_OR_BACKFILL_PLAN.json` holds out approximately 20% of encounter IDs before fitting and compares repeated-perk and top-tier artifact frequencies. The capped-model historical backfill check held out 295 eligible artifacts: 86 had repeated perks versus 86.5 predicted; 161 had a top-tier row versus 166.8 predicted. This is a descriptive check, not proof of independence; repeated encounters and scanner bias can affect both portions. The detailed report stays Git-ignored beside the previews.

V2 account-history reconciliation and separately opted-in aggregate reporting are described in [crafting statistics v2](crafting-statistics-v2.md). Live research remains disabled pending acceptance; the local observed-statistics workflow below remains unchanged.

**Crafting Stats** contains personal observations, community observations, the crafted item log and scanner diagnostics. The Crafting Scanner retains its seven headline totals and a Crafting Stats link. Both pages use the same canonical saved log; there is no separate history store. Every canonical logged item participates automatically, and Keep adds an item to Collection. Not collected does not mean rejected.

The collector remains authoritative for encounter identity, duplicate prevention, strongest OCR candidates, corrections, artwork, persistence, exports and clearing. Statistics read a lightweight projection of those same records and subscribe to log changes. They never write Collection, upload data, or request capture permissions. A retry updates the existing ID; independently encountered items with identical stats remain separate. Crafting logging and local saving are automatic, with no log/save checkboxes. Obsolete saving preferences are ignored. Existing exports, clearing and planner backups cover the data; storage failures remain visible.

**Crafted since last kept** counts new canonical log items since the last successful Keep action. Retries and corrections do not increment it; repeated Keep updates do not reset it again. It persists through reopening, exports and clearing detailed history. Legacy logs seed the count from their available item order.

**Scanner diagnostics** lists missing artifact names and unknown perk labels, linked to the existing log's name field. Resolving a name removes its review entry without creating an item or changing inventory. Future title reads retain rejected OCR text and confidence alongside the canonical item, and both full-log and evidence exports include the unresolved-name references. Older unnamed items appear automatically even when no title OCR evidence was saved. Separately opted-in remote evidence is described in [OCR feedback](ocr-feedback.md); the release gate remains off.

New log metadata includes capture session ID, live/image/unknown capture source and unknown crafting event ID/source. Existing records remain readable and their capture source stays unknown. Game-version identification is permanently outside scope. Event identification is deferred to a local dataset; there are no required event or session inputs.

Eligibility is fixed in the page: complete records after inference count, including image captures and records with unknown source. Records still missing a recognized stat or percentage are excluded. Any manually entered stat name/value or manually corrected stat record excludes the whole artifact. Artifact-title changes alone do not exclude it. Source and Evidence controls are removed. Hall, category and position remain user filters.

Personal and Community are two views of one page, selected by a top-level toggle. Both show the same headline dashboard and perk columns: Perk, Rating, Items, Item frequency, Rows, three tier frequencies and Copies per artifact. Main tier headers are 1%, 6%, 11%; War headers are 1%, 3%, 6%. Each tier cell contains only its row frequency, including 0% for unobserved tiers. Negative perks use magnitude. Main is the initial Hall selection. All halls uses Low/Mid/High headers and normalizes each row against its own hall before aggregation, so Main 6% is mid while War 6% is high. The three tier columns support header sorting. Counts and raw signed values remain in the data for analysis. A shared Collection Target filter narrows perk rows using saved target membership, including linked stat sources and exclusions. Ratings use the existing shared profile values and target axis mapping, with factory inheritance. Click Rating to sort by importance; search and other sortable headers retain their behavior.

The top dashboard shows exact counts and frequencies for zero through five top-value rolls. Main uses magnitude 11; War uses magnitude 6 and never enters the Main denominator. Each perk row contains exact two-, three-, four- and five-copy counts over the complete eligible-artifact sample. Repetition always uses all positions. The previous cumulative frequency column and largest-group table are removed.

The page filter bar groups View, the shared Main/War/All Hall toggle, Collection Targets, category and view-specific controls, search, and scanner navigation. Dashboard cards have no separate Hall controls. Collection Targets uses the same checkbox dropdown styling as Crafted Collection; selecting multiple targets filters perk rows to the union of their included stats. Clearing all selections shows every stat. Selection applies to both Personal and Community without changing saved target definitions or profile comparison selections. Crafted Collection now places its existing comparison-target picker inside the collection filter bar in both List and Structured views.

The UI no longer includes the separate threshold estimator or redundant selected-perk value table. The pure analysis helper retains its threshold/projection API for compatibility; these estimates are not presented as established game probabilities.
